# ADR-004: ULID vs UUIDv4 for Primary Keys

**Статус:** ACCEPTED
**Дата:** 2026-05-04

---

## Контекст

Мастер-план (§1) требует ULID вместо UUIDv4 для предотвращения фрагментации B-tree индексов. Финансовая система генерирует высокий объём INSERT-операций (транзакции, sync events).

## Рассмотренные варианты

| Критерий | UUIDv4 | UUIDv7 | ULID |
|---|---|---|---|
| Сортируемость | ❌ Случайный | ✅ Timestamp-first | ✅ Timestamp-first |
| B-tree фрагментация | 🔴 Высокая | 🟢 Низкая | 🟢 Низкая |
| Стандарт | RFC 4122 | RFC 9562 (2024) | Неформальный |
| Postgres native | `gen_random_uuid()` | Нет native | Нет native |
| Размер | 128 bit | 128 bit | 128 bit |
| Читаемость | Низкая | Средняя | Высокая (Crockford Base32) |
| Монотонность | ❌ | ✅ | ✅ (в пределах мс) |

## Решение

**ULID** — для всех первичных ключей во всех таблицах.

## Обоснование

1. **Хронологическая сортировка** — ULID содержит 48-bit timestamp. `ORDER BY id` = `ORDER BY created_at` без дополнительного индекса.
2. **B-tree friendly** — последовательная вставка вместо случайной → меньше page splits → выше производительность INSERT.
3. **Crockford Base32** — 26 символов, case-insensitive, легко копируются. Удобнее UUIDv7 для логов и отладки.
4. **Совместимость** — хранится как `CHAR(26)` или `BYTEA(16)`. Библиотека `ulid` доступна для Node.js.

## Последствия

- Все `id` столбцы: тип `CHAR(26)` (или custom domain `ULID`)
- Генерация на application layer (Node.js), не в БД
- Библиотека: `ulid` или `ulidx` (TypeScript-native)
- Нет `gen_random_uuid()` в миграциях — генерация всегда в коде
- Для FK: тот же тип `CHAR(26)`
